# Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A VitePress site in `site/` (served at https://wiringk8s.xyz): a landing page with an OS-detected Download button, and guide and developer docs that pull their text from the README and `docs/*.md`.

**Architecture:** `site/` is a self-contained VitePress 1.6.4 project with its own `package.json` and `pnpm-lock.yaml`. The app's dependency tree, `tsconfig.json` and Vitest config are not touched. The README gains `<!-- #region name -->` markers, and the docs pages include those regions with `<!--@include: ../../README.md#name-->`. VitePress pastes included text verbatim, so a small markdown-it plugin rewrites the README's repository-relative links. A Vitest guard fails on includes that VitePress would silently get wrong. The Doppler theme tokens map onto VitePress CSS variables, and the site is dark only. A pure `pickAsset(assets, os)` chooses the installer, and a Vue component fetches the latest release in the browser. Before that fetch, and without JavaScript, the button links to the releases page. CI builds and tests the site. `site/deploy.sh` rsyncs the build to the droplet by hand.

**Tech Stack:** VitePress 1.6.4 (Vue 3.5, Vite 5.4), Vitest 3.2.7, `@vitejs/plugin-vue` 5.2.4, `@fontsource-variable/geist` 5.3.0, pnpm 9, Node 22, GitHub Actions, rsync and nginx on the droplet.

## Deviations from the spec

1. **Hosting (the user changed it twice):** there is no GitHub Pages and no `/wiring/` sub-path. The site has its own domain, **https://wiringk8s.xyz**, served by nginx on the user's DigitalOcean droplet (`root@137.184.51.178`), the same droplet as aftergram.cc and keyorra.com.
   - `base` is `/`.
   - `pages.yml` and `actions/deploy-pages` are dropped. CI builds and tests the site on pushes and pull requests but does not deploy.
   - `site/deploy.sh` builds the site and rsyncs it to `root@137.184.51.178:/var/www/wiring/`; the controller runs it by hand.
   - DNS, the certificate, the nginx site and the repository homepage URL are in "After merge (controller)".
   - The README links to https://wiringk8s.xyz.
2. **Includes are pasted verbatim.** VitePress (`processIncludes`) does not rewrite relative links in included text, so the README's `docs/images/graph.png`, `LICENSE`, `examples/demo/…` and `docs/*.md`, and the `../…` links in `docs/code-signing.md`, would resolve against the including page. The result would be dead links or a build error. `site/.vitepress/repo-links.ts` is a markdown-it plugin that fixes this:
   - documents that have a site page link to that page;
   - screenshots link to `/images/…`, which `site/scripts/copy-assets.mjs` copies from `docs/images` into `site/public/images` before every dev run and build;
   - every other repository path links to GitHub (`tree/master/…` for folders, `blob/master/…` for files).
3. **Bad includes do not fail the build.** An include whose file is missing stays an HTML comment and renders nothing. One whose `#region` is missing includes the **whole** README. Neither is an error. `site/test/includes.test.ts` checks that every include's file and region exist. Dead links do fail `vitepress build`; this was verified.
4. **Developer docs are five pages, not three.** `docs/code-signing.md` and `docs/updates.md` each start with their own `#` title, so each gets a page of its own: Releasing, Code signing and Automatic updates, under a "Releasing" sidebar group. The guide's **Updates** page is the README's user-facing `updates` region, and links to the developer page.
5. **One README edit besides the markers:** the logs screenshot moves from after the Terminal paragraph to the end of the Logs list, so the `logs` region carries it. It sits two paragraphs higher, still in the Features section.
6. **Vitest 3.2.7 in `site/`, not the app's Vitest 5:** Vitest 5 needs Vite 6 or newer, and VitePress 1.6.4 is built on Vite 5. `vite` is pinned to `5.4.21` in `site/package.json`, so the site has a single Vite.
7. **`srcExclude` is not needed.** `srcDir` is `site/`, `docs/` lies outside it, and VitePress already skips `node_modules`. Dark only is `appearance: "force-dark"`, which hides the toggle. Code blocks use the bundled Shiki theme `dracula` (purple, pink, green and cyan) in place of the default `github-dark`, which pairs blue with yellow.
8. **The Namespaces and RBAC page** includes the `namespaces` region and, again, the `navigator` region (which holds the RBAC strike-through text), plus a two-sentence intro and a short pointer to the graph's RBAC chips. The README has no separate RBAC paragraph to include.

- [ ] **Step 1: Insert the markers with a one-off script**

The script matches each region's first and last lines by their exact opening text, so it fails loudly if the README has drifted. It is not committed.

Run:

```bash
python3 - <<'EOF'
from pathlib import Path

```ts
// The README and docs/*.md are written for GitHub, so their relative links point into the
// repository. VitePress pastes included text as-is, which would resolve those links against the
// including page. This rewrites them: documents that have a site page link to it, screenshots
// come from the public folder, and everything else in the repository links to GitHub.
import type { MarkdownRenderer } from "vitepress";

export const REPO_URL = "https://github.com/skensell201/wiring";

const PAGES: Record<string, string> = {
  "README.md": "/guide/getting-started",
  "docs/ipc-contract.md": "/develop/ipc-contract",
  "docs/code-signing.md": "/develop/code-signing",
  "docs/updates.md": "/develop/updates",
};

const REPO_PREFIXES = ["docs/", "examples/", ".github/", "src/", "src-tauri/"];
const REPO_FILES = ["LICENSE", "README.md", "package.json"];

/** The site URL for a repository-relative link, or null to leave the link alone. */
export function rewriteRepoLink(href: string): string | null {
  if (/^[a-z][a-z0-9+.-]*:/i.test(href) || href.startsWith("/") || href.startsWith("#")) return null;
  // docs/*.md link to the repository root with "../".
  const path = href.replace(/^\.\//, "").replace(/^\.\.\//, "");
  const hashAt = path.indexOf("#");
  const file = hashAt === -1 ? path : path.slice(0, hashAt);
  const hash = hashAt === -1 ? "" : path.slice(hashAt);
  if (file in PAGES) return PAGES[file] + hash;
  if (file.startsWith("docs/images/")) return "/images/" + file.slice("docs/images/".length);
  if (REPO_FILES.includes(file) || REPO_PREFIXES.some((p) => file.startsWith(p))) {
    return `${REPO_URL}/${file.endsWith("/") ? "tree" : "blob"}/master/${file}${hash}`;
  }
  return null;
}

/** markdown-it plugin: applies rewriteRepoLink to every link href and image src. */
export function repoLinks(md: MarkdownRenderer): void {
  md.core.ruler.push("wiring_repo_links", (state) => {
    for (const block of state.tokens) {
      for (const token of block.children ?? []) {
        const attr = token.type === "link_open" ? "href" : token.type === "image" ? "src" : null;
        if (!attr) continue;
        const value = token.attrGet(attr);
        const rewritten = value === null ? null : rewriteRepoLink(value);
        if (rewritten !== null) token.attrSet(attr, rewritten);
      }
    }
  });
}
```

The core rule runs after parsing and before rendering. VitePress's own link renderer (base, clean URLs, the dead-link check) therefore sees the rewritten hrefs. Absolute `/images/…` paths are served from `site/public`.

```ts
// Picks the installer to offer on the landing page. Pure, so it is unit-tested; the component
// that fetches the latest release lives in components/HeroActions.vue.

export type Os = "mac" | "windows" | "linux" | "unknown";

export interface ReleaseAsset {
  name: string;
  browser_download_url: string;
}

export interface Download {
  /** What the button says, e.g. "Download for macOS". */
  label: string;
  href: string;
  /** "asset": a direct installer link; "source": the build instructions; "releases": the list. */
  kind: "asset" | "source" | "releases";
}

export const RELEASES_URL = "https://github.com/skensell201/wiring/releases/latest";
export const LATEST_RELEASE_API = "https://api.github.com/repos/skensell201/wiring/releases/latest";
/** The Development page, relative to the site base; the component adds the base. */
export const BUILD_FROM_SOURCE_PATH = "/develop/";

export const OS_NAMES: Record<Exclude<Os, "unknown">, string> = {
  mac: "macOS",
  windows: "Windows",
  linux: "Linux",
};

/** What every visitor gets before the release is known, and without JavaScript. */
export function fallbackDownload(): Download {
  return { label: "Download Wiring", href: RELEASES_URL, kind: "releases" };
}

export function detectOs(userAgent: string, platform = ""): Os {
  const s = `${platform} ${userAgent}`.toLowerCase();
  if (/iphone|ipad|android/.test(s)) return "unknown";
  if (/mac/.test(s)) return "mac";
  if (/win/.test(s)) return "windows";
  if (/linux|x11|cros/.test(s)) return "linux";
  return "unknown";
}

/** The installer for `os` among a release's assets, preferring the NSIS -setup.exe on Windows. */
export function pickAsset(assets: ReleaseAsset[], os: Os): Download {
  if (os === "linux") {
    return { label: "Build from source", href: BUILD_FROM_SOURCE_PATH, kind: "source" };
  }
  if (os === "unknown") return fallbackDownload();
  const suffixes = os === "mac" ? [".dmg"] : ["-setup.exe", ".msi"];
  for (const suffix of suffixes) {
    const asset = assets.find((a) => a.name.endsWith(suffix));
    if (asset) {
      return { label: `Download for ${OS_NAMES[os]}`, href: asset.browser_download_url, kind: "asset" };
    }
  }
  return { label: `Download for ${OS_NAMES[os]}`, href: RELEASES_URL, kind: "releases" };
}
```

// The landing page's download area. It renders the releases-page fallback on the server, so the
// button works without JavaScript; in the browser it detects the OS and links the installer from
// the latest release, keeping the fallback when the GitHub API cannot be reached.
import { onMounted, ref } from "vue";
import { withBase } from "vitepress";
import {
  LATEST_RELEASE_API,
  OS_NAMES,
  RELEASES_URL,
  detectOs,
  fallbackDownload,
  pickAsset,
  type Download,
  type Os,
  type ReleaseAsset,
} from "../download";

type Platform = Exclude<Os, "unknown">;
const PLATFORMS: Platform[] = ["mac", "windows", "linux"];

const primary = ref<Download>(fallbackDownload());
const detected = ref<Os>("unknown");
const others = ref(PLATFORMS.map((os) => ({ os, download: pickAsset([], os) })));

const href = (d: Download) => (d.kind === "source" ? withBase(d.href) : d.href);

async function latestAssets(): Promise<ReleaseAsset[]> {
  try {
    const res = await fetch(LATEST_RELEASE_API, { headers: { Accept: "application/vnd.github+json" } });
    if (!res.ok) return [];
    const release = (await res.json()) as { assets?: ReleaseAsset[] };
    return release.assets ?? [];
  } catch {
    return [];
  }
}

onMounted(async () => {
  detected.value = detectOs(navigator.userAgent, navigator.platform);
  if (detected.value === "linux") primary.value = pickAsset([], "linux");
  const assets = await latestAssets();
  if (detected.value !== "unknown") primary.value = pickAsset(assets, detected.value);
  others.value = PLATFORMS.filter((os) => os !== detected.value).map((os) => ({
    os,
    download: pickAsset(assets, os),
  }));
});
</script>

## After merge (controller)

These are outward actions (registrar, DNS, droplet, GitHub settings). They are not plan tasks. They follow the droplet's pattern for adding a site, the same as for aftergram.cc and keyorra.com. The pattern is in memory `skensel-droplet.md`.

1. **DNS.** At GoDaddy, delegate `wiringk8s.xyz` to DigitalOcean (`ns1.digitalocean.com`, `ns2.…`, `ns3.…`) if it is not delegated already. In DigitalOcean → Networking → Domains, add `wiringk8s.xyz` with these records:
   - `A @ → 137.184.51.178`
   - `CNAME www → @`

   Wait until `dig +short wiringk8s.xyz` and `dig +short www.wiringk8s.xyz` both answer `137.184.51.178`.

2. **Webroot, and a first deploy so there is something to serve.** On the server run `mkdir -p /var/www/wiring`. From the merged `master` on the Mac, run `site/deploy.sh`. Expected: the rsync file list, then `Deployed to root@137.184.51.178:/var/www/wiring/ — https://wiringk8s.xyz`.

3. **HTTP-only server block.** Write `/etc/nginx/sites-available/wiring` with:

   ```nginx
   server {
       listen 80;
       listen [::]:80;
       server_name wiringk8s.xyz www.wiringk8s.xyz;
       root /var/www/wiring;

       location /.well-known/acme-challenge/ { root /var/www/wiring; }
       location / { try_files $uri $uri.html $uri/ =404; }
   }
   ```

   Then run `ln -s /etc/nginx/sites-available/wiring /etc/nginx/sites-enabled/wiring && nginx -t && systemctl reload nginx`.

4. **Certificate.** Run `certbot certonly --webroot -w /var/www/wiring -d wiringk8s.xyz -d www.wiringk8s.xyz`. Expected: `Successfully received certificate`, saved under `/etc/letsencrypt/live/wiringk8s.xyz/`.

5. **Final config.** Copy `/etc/nginx/sites-available/ivan_kostin` to `/etc/nginx/sites-available/wiring` and adapt it:
   - the server names: `wiringk8s.xyz` and `www.wiringk8s.xyz`;
   - the certificate paths: `live/wiringk8s.xyz`;
   - the root: `/var/www/wiring`;
   - the location: `try_files $uri $uri.html $uri/ =404;`, which serves VitePress's clean URLs, so `/guide/graph` serves `guide/graph.html` and `/develop/` serves `develop/index.html`;
   - `error_page 404 /404.html;`.

   Copy the `add_header` lines (HSTS and the security headers), the `ssl_*` lines and the `limit_req` / `limit_conn` values from `ivan_kostin` verbatim. The zones `general` and `addr` are defined in `nginx.conf`. The result has this shape:

   ```nginx
   # HTTP: ACME challenges, everything else to HTTPS on the apex.
   server {
       listen 80;
       listen [::]:80;
       server_name wiringk8s.xyz www.wiringk8s.xyz;
       location /.well-known/acme-challenge/ { root /var/www/wiring; }
       location / { return 301 https://wiringk8s.xyz$request_uri; }
   }

   # HTTPS www → apex.
   server {
       listen 443 ssl;
       listen [::]:443 ssl;
       http2 on;
       server_name www.wiringk8s.xyz;
       ssl_certificate     /etc/letsencrypt/live/wiringk8s.xyz/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/wiringk8s.xyz/privkey.pem;
       return 301 https://wiringk8s.xyz$request_uri;
   }

   # HTTPS apex: the site.
   server {
       listen 443 ssl;
       listen [::]:443 ssl;
       http2 on;
       server_name wiringk8s.xyz;
       ssl_certificate     /etc/letsencrypt/live/wiringk8s.xyz/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/wiringk8s.xyz/privkey.pem;

       root /var/www/wiring;
       index index.html;

       # HSTS and security headers, and the ssl_* lines: copied verbatim from ivan_kostin.
       # limit_req zone=general …; limit_conn addr …;  (values as in ivan_kostin)

       location / {
           try_files $uri $uri.html $uri/ =404;
       }
       # Hashed build assets never change.
       location /assets/ {
           expires 1y;
           add_header Cache-Control "public, immutable";
       }
       error_page 404 /404.html;
   }
   ```

   An `add_header` inside `location /assets/` replaces the server-level headers for that location. Either repeat the security headers there, or drop that block if `ivan_kostin` has no equivalent. Run `nginx -t && systemctl reload nginx`. Expected: `syntax is ok` and `test is successful`.

6. **Renewal.** Run `certbot renew --dry-run`. Expected: `Congratulations, all simulated renewals succeeded`, with wiringk8s.xyz in the list.
